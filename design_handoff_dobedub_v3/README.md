# Handoff: DOBEDUB STUDIO v3 프론트엔드 재설계

## Overview
DOBEDUB STUDIO v3의 화면 전체를 업무 흐름 기준으로 재설계한 결과물과, 그 설계를 현재 코드(`backend/app`, `frontend/src`)와 대조한 점검 결과를 함께 전달합니다.
목표는 두 가지입니다. (1) 코드에는 있으나 화면에 없던 기능을 화면으로 만들고, (2) 화면이 요구하지만 코드에 없는 API·테이블을 신설합니다.

대상 저장소: `changkyuneun-ux/dobedub_studio_v3` (branch `main`)
작업 디렉토리: `comfyui-video-studio-app-v4` — 이 폴더를 그 루트에 두고 시작합니다.
기준 시점: commit `a27ced5089db` · 2026-08-10 재점검

## 이 작업의 성격 — 부분 수정이 아니라 전면 재구축

**기존 화면을 손보는 작업이 아닙니다.** 현재 `frontend/src`의 화면은 이번 설계로 대체됩니다. 기존 컴포넌트에 기능을 덧붙이거나 스타일만 바꾸는 방식으로 진행하지 마십시오.

### 무엇이 달라지는가

| | 구버전 | 이번 설계 |
|---|---|---|
| 화면 구성 | 기능 단위로 흩어진 페이지 | 업무 흐름 단계(S1→S5)로 묶인 화면 |
| 레이아웃 | 화면마다 제각각 | 좌측 사이드바 212px + 헤더 + 본문 + 우측 패널의 공통 골격 |
| 상태 표현 | 성공/실패 위주 | 진행·취소 요청·경고·차단·권한 없음·세션 만료까지 명시적으로 |
| 경고 | 없거나 개별 알림 | 규칙 위반(BLOCK)과 필수 누락(WARN)을 한 자리에 통합 |
| 관리자 | 기능별 분산 | 카탈로그 / 워크플로 / 권한·사용자 / 운영 4단계로 재편 |
| 색·타이포 | 혼재 | 아래 Design Tokens 단일 체계 |

### 진행 방식

- 화면을 **새로 만들고 기존 것을 걷어내는 순서**로 진행하십시오. 기존 컴포넌트를 수정해 설계에 맞추려 하면 구버전 구조가 그대로 남습니다.
- 재사용할 것은 **로직**입니다. API 호출, 상태 관리, 유효성 검사, 폼 처리 훅은 최대한 살리십시오. 재사용하지 말아야 할 것은 **화면 구조와 스타일**입니다.
- 기존 컴포넌트를 그대로 쓸지 판단이 서지 않으면 기준은 하나입니다. **설계 파일의 해당 화면과 나란히 놓고 봤을 때 같아 보이는가.** 비슷한 정도면 다시 만드십시오.
- 설계에 없는 기존 UI 요소(버튼, 탭, 패널)를 임의로 남기지 마십시오. 필요하다고 판단되면 남기지 말고 먼저 물어보십시오.
- 공통 골격(사이드바, 헤더, 본문 그리드, 우측 패널)은 화면마다 새로 짜지 말고 레이아웃 컴포넌트로 한 번 만들어 전 화면이 공유하게 하십시오. 설계 파일에서 이 골격은 모든 화면에 동일하게 반복됩니다.

### 예외

`0 Structure Options.dc.html`(`1a` `1b` `1c`)은 초기 방향안이라 구현 대상이 아닙니다. 그 외 모든 화면은 이번 설계가 최종안입니다.

## About the Design Files
이 번들의 `.dc.html` 파일은 **HTML로 만든 디자인 레퍼런스**입니다. 그대로 배포하거나 복사해 넣을 production 코드가 아닙니다.
할 일은 이 화면들을 **대상 코드베이스의 기존 환경(React + TypeScript, `frontend/src`)에서 그 환경의 패턴과 라이브러리로 다시 구현**하는 것입니다. 마크업 구조나 클래스 이름을 그대로 옮기지 마십시오.

각 파일은 브라우저에서 바로 열립니다. 화면마다 `1a`, `2c`, `7g` 같은 고정 id가 붙어 있고, 이 문서의 모든 참조는 그 id를 씁니다.

## Fidelity
**High-fidelity.** 색상·타이포·간격·상태 표현이 최종안입니다. 구버전 화면의 색이나 간격을 기준으로 절충하지 마십시오. 아래 Design Tokens의 값을 그대로 쓰되, 코드베이스에 이미 동일 역할의 토큰이 있으면 그쪽을 우선합니다.
단, 데이터는 전부 예시입니다. 숫자·이름·프롬프트 문구는 실제 API 응답으로 대체하십시오.

## Interactions & Behavior

**공통**
- 권한이 없는 메뉴는 사이드바에서 숨깁니다. 직접 URL 진입만 `7g`의 403 화면에 도달합니다.
- 서버 오류 표시 위치: 사용자가 누른 동작(저장·실행)은 그 버튼 근처, 화면 진입 조회 실패는 본문 자리.
- 서버가 `detail` 문구를 주면 그대로 노출하고, 없을 때만 한국어 기본 안내로 대체합니다.

**2b 프롬프트 경고**
- `severity`가 차단성이면 적용 버튼을 비활성화하고 배지를 BLOCK으로, 경고성이면 진행 가능 상태로 둡니다.
- 경고는 좌측 본문 상단에 스트립으로 모읍니다. 오른쪽 패널로 분산하지 마십시오.

**2c 취소**
- 취소를 누르면 버튼이 `Cancelling…`으로 바뀌고 재클릭이 막힙니다.
- 취소 요청 중에는 워크플로 선택·키프레임 교체·세그먼트 파라미터·새 작업 제출이 모두 잠깁니다.
- 요청이 실패하면 버튼이 다시 활성화되고 오류 문구가 그 자리에 표시됩니다.

**3a 삭제**
- 진행 중(IN_PROGRESS) 작업은 삭제 버튼이 비활성입니다.
- 권한이 없으면 버튼 자체가 보이지 않습니다.
- 확인 창에 작업 id·실행 시각·실행자·결과물 수를 보여주고, 되돌릴 수 없음을 명시합니다.

## State Management
- 인증 토큰과 `expiresAt`은 sessionStorage에 유지(현재 코드 방식 유지). 탭을 닫으면 종료.
- 작업 진행 상태는 `GET /api/jobs/{id}` 폴링. 취소 요청 여부는 클라이언트 플래그로 유지하고 서버 상태와 합성해 표시.
- 프롬프트 생성 결과(positive/negative/warnings)는 세그먼트별로 보관하되, 적용 전까지는 세그먼트 설정에 반영하지 않습니다.
